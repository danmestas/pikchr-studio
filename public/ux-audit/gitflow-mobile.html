Gitflow: authoring on a phone-sized screen

Open the new annotated Gitflow guide. This page preserves the original mobile audit and its test specimen; the guide replaces that sparse specimen as the teaching example.

Computer-use audit · 19 September 2026 · Confirmed browser viewport: 390 × 844 CSS pixels

The branching-strategy suggestion is now a concrete Gitflow example: 13 commit circles, 9 independent labels, and 17 arrows. All 39 objects were created through Studio’s visible controls. No source editing was used during construction.

This was a desktop-pointer exercise at a mobile viewport, not a physical-phone test. Touch accuracy, the on-screen keyboard, and pinch gestures remain unverified. No horizontal page overflow was observed.

What the diagram means

This depicts the classic model described in Vincent Driessen’s original Gitflow article, using main for the original master name. A feature branches from and returns to develop. A release branches from develop and merges into both main and develop. After that release, a hotfix branches from main and returns to both main and develop. Main carries the v1.0, v1.1, and v1.1.1 tags. Arrows indicate progression or merge direction; they are not Git commit-parent pointers. This is a teaching example, not a claim that Gitflow is the best strategy for every project.

The earlier branching example was a proposed category, not an existing template: this is its first concrete specimen.

What was exercised

Persona: a technical-documentation author arranging and revising a branching diagram on a phone-sized browser. The session covered creating repeated commits and text, selecting and navigating a dense canvas, updating labels, adding connectors, changing a route, recovering with Undo, and attempting multi-selection for arrangement.

Creation, labeling, routing, and Undo produced valid rendered source. Undo restored label and route edits. The principal limitations were visibility and interaction cost—not an inability to render this diagram. The mobile first screen showed controls but no canvas, and edit results repeatedly ended up outside the visible screen.

Evidence convention: “Observed” records an action or measured viewport result. “Risk” is an inference about likely touch or authoring impact. “No exposed control found” is limited to the inspected UI, not a statement about the underlying engine. No overall usability score is assigned from this single exercise.

Implementation follow-up — 19 September 2026

Changes have been implemented for all eight findings below. These issues are not marked closed: browser checks at a phone-sized viewport do not substitute for physical-phone touch, keyboard, and gesture acceptance. The original observations are retained as the baseline.

  1. 020 — Canvas-first workspace. Compact mobile actions and collapsed document controls now leave the canvas visible on initial load. At 390 × 844, the measured canvas occupied Y 129–772.
  2. 021 — Visible editing feedback. A bottom inspector keeps the canvas, Undo, and state feedback on screen. During a text edit, the canvas occupied Y 129–396 and Undo Y 81–125. Focus was preserved after Update text, and Undo restored the exact original source.
  3. 022 — Small-target assistance. Nearby selection within a 44-pixel target area and an overlap-choice control have been added. A desktop-pointer click 12 pixels outside D1 selected it successfully. Physical-finger accuracy and crowded-target behavior remain acceptance checks; no touch-success claim is made.
  4. 023 — Keyboard-free multi-selection. Visible Select multiple, clear-selection, and group-movement controls are implemented. Browser testing selected two objects, moved them, and verified exact-source Undo without requiring Shift.
  5. 024 — Contextual focus. Automatic selection focus is capped at 300%, while manual zoom can still reach 1200%. Opening D1’s inspector kept D1 inside the canvas at 300%, with neighboring F2 and R1 visible. Visibility across short screens, keyboard-open states, and different diagram sizes still needs acceptance testing.
  6. 025 — Repeat construction. Repeat last shape preserves text, size, and style, with configurable X/Y offsets and optional preparation of the next position. Browser testing created four shapes at the same X and Y 0, −1, −2, −3. A follow-up naming fix now uses stable sequential IDs instead of accumulating digits; focused regression tests cover it. Tap-to-place has not been implemented.
  7. 026 — Meaningful connector choices. Connector object labels now include endpoint summaries; Link12 displayed R2 → M1 in the browser. New-connector menus omit standalone text by default and expose an explicit text-endpoint option. Existing text connections remain supported.
  8. 027 — Route editing and state guidance. Add bend, delete bend, and reset-route controls are implemented, with guidance reflecting automatic versus queued application. Browser checks exercised addition, deletion, reset, and exact-source Undo. A queued bend showed one queued change and Undo restored its source. Real-phone handle manipulation remains an acceptance check.

Prioritized mobile backlog — original findings

P1 means the issue interrupts a frequent core authoring task. P2 means the task remains possible but incurs substantial navigation or repetition. Address 020–023 first: together they determine whether an author can see, select, edit, and arrange work without repeatedly losing context. The remaining findings improve efficiency and precision.

PKUX-020 · P1 · Controls consume the initial mobile screen

Observed / reproduce
Open a new diagram at 390 × 844. The first screen contains toolbars before the canvas; the canvas is not visible. Disabled selection actions remain visible even with an empty document.
Impact
The author must discover and scroll to the primary workspace before drawing. Frequently used actions compete with document-management and unavailable actions.
Recommendation
Collapse document controls into a menu, show selection actions only when relevant, and budget the initial viewport around a visible canvas with a compact action bar.
Acceptance check
At 390 × 844 and comparable short viewports, a new and a populated document both show a usable canvas and an obvious Add action without scrolling. Selection-only actions do not occupy empty-document space.

PKUX-021 · P1 · Editing separates the controls from their result

Observed / reproduce
Select D1 at fit zoom and choose Edit selected object. The canvas occupied viewport Y −341 to 99 while the text field began at Y 282.5. Updating the text moved focus to the page body and left selected content offscreen. Applying Horizontal first to Link12 produced a valid route, but the canvas bottom was then Y −342.5. Undo was at Y −349.5 and status at Y −1348.5—also offscreen.
Impact
Even a successful operation requires searching for the result, confirmation, and recovery control. This is a mobile follow-up to PKUX-005.
Recommendation
Keep the canvas visible above a compact bottom-sheet inspector, preserve focus and scroll context after submitting edits, and keep Undo plus applied/saved feedback visible.
Acceptance check
Edit D1’s text, route Link12, then Undo at 390 × 844. The selected object or changed route, operation feedback, and Undo remain visible without a page-scroll search; focus stays on a useful control.

PKUX-022 · P1 · Fit zoom produces tiny commit targets

Observed / reproduce
Fit the complete 39-object diagram. D1, F2, and H2 circles each measured approximately 14.19 CSS pixels across at 100% fit. Precise desktop-pointer selection worked; labels were very small.
Risk
Small visible shapes are likely difficult to select with a finger. Actual touch misses were not measured and must not be inferred as a reproduced failure.
Recommendation
Inflate interaction targets without changing diagram geometry. For crowded targets, provide disambiguation or a selection sheet and a readable zoom-to-edit affordance.
Acceptance check
On a physical phone, select D1, F2, and H2 without unintended neighbors. Ensure minimum practical touch targets and an alternative when enlarged hit areas overlap; verify readable editing zoom.

PKUX-023 · P1 · Multi-selection has no exposed touch workflow

Observed / reproduce
The UI instructs Shift-click. Ordinary selection of M0 followed by M1 leaves one object selected and Arrange disabled. No selection mode, checkboxes, or lasso was found in the inspected controls.
Impact
Alignment and multi-object movement exist but lack a discoverable keyboard-free entry point. This extends PKUX-007 and PKUX-016.
Recommendation
Add a visible Select multiple mode with a selected count, clear selection, and selection-aware arrange/move actions. Preserve ordinary single-tap selection outside that mode.
Acceptance check
Without a hardware keyboard, select M0 and M1, align them, move both, then exit multi-select. Each step is discoverable through visible controls and reversible with Undo.

PKUX-024 · P2 · Focus selection loses branch context

Observed / reproduce
Select D1 and choose Focus selection. Zoom jumped to 1200%. The canvas top was approximately Y −21.5 under a sticky toolbar around 140 pixels tall, obscuring the upper node area.
Impact
Focusing a small commit removes neighboring branch context and does not account for the actually visible canvas. This refines PKUX-004.
Recommendation
Fit to the unobscured viewport, add contextual padding or neighboring commits, and cap automatic zoom separately from manual zoom.
Acceptance check
Focus D1 from both the initial and scrolled layouts. D1 is fully visible below overlays, remains readable, and retains useful neighboring context; Fit restores the full diagram.

PKUX-025 · P2 · Repeated commits require repeated coordinate entry

Observed / reproduce
Building 13 commits repeatedly required Label, ID, X/Y, fill, and Add operations. Dimensions persisted, but Y reset to 0 and X used an automatic value. Completing all 39 objects was possible through the forms.
Impact
The author repeatedly translates a visual lane layout into numerical positions. Single-object duplication alone does not provide a fluent repeated-lane workflow; see PKUX-010.
Recommendation
Offer duplicate-and-place, repeat last offset, and click/tap-to-place. Preserve lane and style choices when explicitly repeating a commit.
Acceptance check
Create four evenly spaced same-style commits in one lane without re-entering their shared X coordinate and dimensions. Give each a distinct label and undo the last addition.

PKUX-026 · P2 · Connector choices do not expose their meaning

Observed / reproduce
The created connectors appear as Link1 through Link17 without endpoint summaries. From/To choices include nine title/tag text objects alongside the 13 commits, increasing the number of choices and dropdown steps.
Impact
Finding the intended merge route requires remembering generic IDs and filtering irrelevant text mentally. This is a remaining identity gap from PKUX-011.
Recommendation
Show endpoint labels such as “D0 → F1” in connector lists. Default endpoint pickers to connectable shapes, with text endpoints available explicitly, and support direct endpoint picking.
Acceptance check
Locate a feature-merge arrow and create a hotfix-merge arrow without memorizing Link numbers. Ordinary endpoint selection omits headings and tags while still offering an explicit way to connect text if desired.

PKUX-027 · P2 · Routing guidance and route controls remain incomplete

Observed / reproduce
With automatic application enabled, routing guidance still says to release to review valid code. A Horizontal first route applied successfully, but its result was offscreen. No arbitrary bend insertion/deletion controls were exposed.
Impact
The author cannot reliably tell whether an edit is pending or committed, and cannot freely shape longer merge paths. This follows up PKUX-005 and the existing open PKUX-014; it is not a new claim that basic routing fails.
Recommendation
Make guidance reflect the active apply mode and show local committed/pending feedback. Add discoverable bend insertion, deletion, and route reset after the visibility issues are fixed.
Acceptance check
In both auto-apply and queued modes, reroute a merge arrow and identify its state without scrolling. Insert and remove a bend, reset the route, and Undo each operation while endpoints stay attached.

Next test pass

  1. On a physical phone, edit a commit label with the keyboard open, change a merge route, and Undo while keeping the result and state feedback visible.
  2. Select small or overlapping commits, enter multi-select, align and move a lane, then clear selection without a hardware keyboard.
  3. Verify contextual focus in portrait, landscape, and short screens. Repeat a four-commit lane, assign distinct labels, and Undo the final addition.
  4. Create and reconnect a hotfix merge, including an existing text endpoint. Insert, delete, and reset bends in both auto-apply and queued modes, then verify recovery.
  5. Verify two-finger pan/pinch, gesture cancellation, and keyboard resize behavior. This audit supplies no physical-phone pass/fail evidence for those behaviors. Consider tap-to-place separately after testing the new repeat workflow.
